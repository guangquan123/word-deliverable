# Markdown → body blocks 转换规则

本文件是 `word-deliverable` skill 的内容转换桥接规则，指导 agent 将用户提供的 Markdown / 纯文本 / 飞书文档内容转换为 spec.json 的 `body` block 列表。

核心原则：**内容层级决定 Heading，Heading 决定 Word 结构，多级列表只负责显示编号。** 不得根据 Markdown `#` 数量机械确定最终 Word 层级。`layout_profile` 只控制版式，不影响这里的内容映射：默认 `government`，也可用 `consulting`、`technical`、`reader`；不要把它与 `numbering_profile` 混淆。

---

## 1. 先识别"文档标题"

Markdown 最前面的 `# 标题` 可能只是**文档名称**，而不是正文"一级章节"。

### 判定规则

如果 Markdown 最前面的 `# 标题`：

- 位于全文最前部
- 全文只有一个同等级总标题
- 内容明显属于文件名称
- 后续标题均从 `##` 或更深层开始

则将其识别为 **Document Title**，不参与正文章节自动编号。

### 示例

```markdown
# XX平台建设实施方案

## 建设总览

### 建设目标
```

正确转换：

- `document_title`: "XX平台建设实施方案"（填入 spec，不进 body，不编号；未设 doc_name 时可作封面文档名兜底）
- body 最浅层 `## 建设总览` → H1（第一章 建设总览）
- `### 建设目标` → H2（1.1 建设目标）

错误转换（禁止）：

- `# XX平台建设实施方案` → H1（第一章 XX平台建设实施方案）← 文档标题被误编为第一章
- `## 建设总览` → H2（1.1 建设总览）← 层级全部错位

---

## 2. 相对层级映射

识别文档标题后，**剩余正文最浅层标题作为 H1**，逐层下推。不要机械执行 `# = H1 / ## = H2`。

### 示例

```markdown
# XX平台建设实施方案

## 建设方法

### 核心模块设计

#### 自顶向下识别

##### 流程材料识别

###### 表单信息提取
```

| Markdown | Word Heading | 显示编号（formal） |
|----------|-------------|-------------------|
| `# XX平台建设实施方案` | Document Title（不编号） | 封面文档名 |
| `## 建设方法` | Heading 1 | 第一章 建设方法 |
| `### 核心模块设计` | Heading 2 | 1.1 核心模块设计 |
| `#### 自顶向下识别` | Heading 3 | 1.1.1 自顶向下识别 |
| `##### 流程材料识别` | Heading 4 | 1.1.1.1 流程材料识别 |
| `###### 表单信息提取` | Heading 5 | （1） 表单信息提取 |

---

## 3. 标题跳级处理

标题层级原则上不得跳级。

### 示例

```markdown
## 建设方法

#### 模块划分
```

上级是 `##`（将映射为 H1），下一标题直接跳到 `####`（将映射为 H3）。

### 处理规则

- **能明确判断是 Markdown 编写错误**：规范为连续结构（H1 → H2），即 `#### 模块划分` 降为 H2。
- **无法可靠判断**（可能代表真实业务结构）：保留内容，不编造中间标题，采用最接近的连续 Word 层级，并在 validate_docx.py 质量检查中记录该结构异常。
- **禁止**自行创造不存在的中间章节名称。

---

## 4. 已有手工编号的去除

输入内容可能已包含手工章节编号：

```markdown
## 2. 建设方法
### 2.1 模块设计
#### 2.1.1 自顶向下识别
```

### 处理规则

1. 保留标题文字
2. 去除原手工章节编号（"2." / "2.1" / "2.1.1"）
3. 使用 Word 自动多级编号重新生成

转换后 body：

```json
{"type": "h1", "text": "建设方法"},
{"type": "h2", "text": "模块设计"},
{"type": "h3", "text": "自顶向下识别"}
```

最终不得出现"1.1 2.1 模块设计"这样的重复编号。

### 但禁止误删正文中的数字

以下数字属于标题真实内容，**不得作为手工编号删除**：

```markdown
### A1-A5 能力分层
### ISO 8000 标准
### 2026 年建设计划
```

其中 `A1-A5` / `ISO 8000` / `2026` 是标题真实内容。

**判定标准**：只有明确位于标题开头、并符合章节编号结构（`数字.` 或 `数字.数字.数字`）的数字才可以去除。`A1-A5`（字母开头）、`ISO 8000`（字母开头）、`2026 年`（带"年"）均不符合，应保留。

---

## 5. 标题与列表区分

以下内容不一定是标题：

```markdown
1. 收集材料
2. 识别对象
3. 开展评审
```

### 判定标准

- **标题**承担**章节组织作用**——出现在导航窗格、成为目录结构节点、承担明确父子章节关系 → 用 Heading
- **列表**承担**同一章节内部的信息枚举作用** → 用 Word 原生编号列表（`list` block）

如果语义只是步骤/条目，应转换为 `list` block，**不得因为有编号就转成 Heading**。

---

## 6. 小节标题与 Heading 区分

类似"执行口径"、"案例说明"、"注意事项"、"判断规则"等内容：

- 如果仅承担当前段落内部的提示作用 → 使用 **小节标题** Style（`note` block），不进目录
- 如果需要出现在导航窗格、成为目录结构节点、承担明确父子章节关系 → 使用 Heading

**判断原则**：如果不确定，问自己"这个标题需要出现在目录里吗？"——不需要则用小节标题，需要则用 Heading。**不得为视觉强调随意升级为 Heading 3/4/5。**

---

## 7. 生成前必须建立标题树

在写入 spec.json 的 body 之前，先解析全部输入内容并建立完整标题树，确认父子关系合理后才开始生成 body 列表。

### 示例标题树

```text
Document Title: XX平台建设实施方案
│
├── H1 建设方法
│   ├── H2 核心模块设计
│   │   ├── H3 自顶向下识别
│   │   │   ├── H4 流程材料识别
│   │   │   │   ├── H5 表单识别
│   │   │   │   │   └── H6 字段识别
```

只有标题树确认合理以后，才能开始生成 body block 列表。**不得边读 Markdown 边临时猜标题样式。**

---

## 8. H5/H6 的特殊处理

H5 和 H6 使用**局部编号**（formal Profile 下显示 `（1）` / `1）`），与 H1-H4 的继承编号不同：

- H5 在每个 H4 下重新从（1）开始编号
- H6 在每个 H5 下重新从 1）开始编号
- **但 Word 内部仍必须是 Heading 5 / Heading 6 Style**，不得降级为 Normal 或普通列表

转换时：如果 Markdown 有 5-6 层结构，直接用 `h5` / `h6` block 类型，脚本会自动处理局部编号。

---

## 9. Numbering Profile 选择

根据文档类型选择合适的 Numbering Profile：

| 文档类型 | 推荐 Profile | 一级显示 | 适用场景 |
|---------|-------------|---------|---------|
| 实施方案 / 规格说明书 / 标准规范 / 调研报告 / 技术方案 | `formal`（默认） | 第一章 | 长篇正式文档 |
| 会议纪要 / 工作记录 / 周报 / 简报 | `lightweight` | 一、 | 轻量文档 |

### formal Profile 编号体系

| Heading | 显示编号 | 说明 |
|---------|---------|------|
| H1 | 第一章 | `chapter_num_format` 控制中文/阿拉伯 |
| H2 | 1.1 | 继承一级 |
| H3 | 1.1.1 | 继承一二级 |
| H4 | 1.1.1.1 | 继承一二三级 |
| H5 | （1） | 局部编号，每个 H4 下重置 |
| H6 | 1） | 局部编号，每个 H5 下重置 |

### lightweight Profile 编号体系

| Heading | 显示编号 | 说明 |
|---------|---------|------|
| H1 | 一、 | 中文计数 |
| H2 | （一） | 中文计数，每个 H1 下重置 |
| H3 | 1. | 阿拉伯，每个 H2 下重置 |
| H4 | （1） | 阿拉伯，每个 H3 下重置 |
| H5 | 1） | 阿拉伯，每个 H4 下重置 |
| H6 | ① | 圈码（脚本用 decimal 兜底，Word 中可手动调整） |

**注意**：无论采用哪种 Profile，**Heading 层级本身不能丢失**。lightweight Profile 下 `chapter_num_format` 不生效（一级固定"一、"）。

## 10. 表格、宽表与图片映射

- Markdown 表格或同维度对比数据转换为 `table` block；`headers` 必须非空，每行列数一致。
- `widths` 是正数权重而非必须合计 100 的百分比；脚本会归一化并结合当前 Section 可用宽度落地。
- 列数 `>=7` 或内容明确需要横向展示时，可设 `"landscape": true`；脚本仅将该表所在 Section 横向，随后恢复纵向。
- 默认不要生成 `figure` block。只有用户提供了图片并明确要求插入时，才设置顶层 `"include_figures": true` 并写入图片路径；相对路径以 `spec.json` 所在目录为基准。

## 11. 完整转换示例

### 输入 Markdown

```markdown
# XX平台建设实施方案

## 建设方法

### 核心模块设计

#### 自顶向下识别

##### 流程材料识别

###### 表单信息提取

具体步骤：

1. 收集业务表单
2. 提取字段信息
3. 识别业务对象

**执行口径**：以业务部门确认的表单为准。

### 自底向下识别

#### 数据库表分析
```

### 转换后的 spec.json 片段

```json
{
  "document_title": "XX平台建设实施方案",
  "doc_name": "XX平台建设实施方案",
  "numbering_profile": "formal",
  "toc_levels": "1-3",
  "body": [
    {"type": "h1", "text": "建设方法"},
    {"type": "h2", "text": "核心模块设计"},
    {"type": "h3", "text": "自顶向下识别"},
    {"type": "h4", "text": "流程材料识别"},
    {"type": "h5", "text": "表单信息提取"},
    {"type": "p", "text": "具体步骤："},
    {"type": "list", "ordered": true, "items": ["收集业务表单", "提取字段信息", "识别业务对象"]},
    {"type": "note", "title": "执行口径", "text": "以业务部门确认的表单为准。"},
    {"type": "h2", "text": "自底向下识别"},
    {"type": "h3", "text": "数据库表分析"}
  ]
}
```

### 注意

- `# XX平台建设实施方案` → `document_title`，不进 body
- `## 建设方法` → H1（最浅层升为一级）
- `### 核心模块设计` → H2
- `#### 自顶向下识别` → H3
- `##### 流程材料识别` → H4
- `###### 表单信息提取` → H5（局部编号（1））
- `1. 收集业务表单` → list（不是 Heading）
- `**执行口径**` → note（小节标题，不进目录）
